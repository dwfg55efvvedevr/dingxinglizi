# v2.1 Evolution Core — Requirements and Acceptance Baseline

Status: `APPROVED_FOR_BUILD`

Version target: `2.1.0`

Authority: current user request, repository `AGENTS.md`, v2.0 contracts and tests.

## 1. Outcome

Add a project-local, deterministic learning loop that can:

1. initialize an isolated Evolution workspace without overwriting an existing v2 project;
2. collect a sanitized outcome from a structurally validated completed run;
3. record explicit, evidence-linked feedback;
4. generate an evidence-oriented retrospective;
5. create draft improvement proposals only when evidence is sufficient;
6. create draft regression-evaluation candidates for review;
7. report Evolution status without changing project or Skill state.

The feature is an evidence and proposal system. It is not an autonomous modifier or publisher.

## 2. Scope

The canonical CLI surface is:

```text
orchestrator.py evolution init PROJECT_DIR
orchestrator.py evolution collect PROJECT_DIR [--run-id RUN-ID]
orchestrator.py evolution feedback PROJECT_DIR
  --kind KIND --result RESULT --severity SEVERITY --category CATEGORY
  --summary "SANITIZED SUMMARY" --evidence PROJECT_RELATIVE_PATH [--evidence ...]
  [--run-id RUN-ID] [--task-id TASK-ID] [--role ROLE]
orchestrator.py evolution retrospect PROJECT_DIR [--run-id RUN-ID]
orchestrator.py evolution propose PROJECT_DIR [--retrospective PATH]
orchestrator.py evolution eval-candidates PROJECT_DIR [--proposal PATH]
orchestrator.py evolution status PROJECT_DIR
```

Every successful command prints one JSON object to stdout and exits `0`. Invalid user arguments, a user-supplied path/summary violation, or an operating-system/permission failure prints `ERROR` to stderr and exits `2`. Persisted workspace corruption or an unsupported persisted schema prints one JSON object with `status=BLOCKED` and its reason code to stdout and exits `3`. A valid request blocked by insufficient evidence, ambiguous input, a lock or an incompatible workspace likewise prints one JSON status object and exits `3`. `status` reports `NOT_INITIALIZED` with exit `0`, but reports persisted corruption with exit `3`, because observation does not repair or reinterpret state.

Input selection is deterministic and never uses modification time. When `collect` is called without `--run-id`, exactly one structurally valid completed run must exist; zero returns `INSUFFICIENT_EVIDENCE`, while more than one returns `AMBIGUOUS_INPUT` with exit `3`. `retrospect` without `--run-id` aggregates every validated Evolution record. With `--run-id`, it includes only the matching Outcome and Feedback explicitly linked to that run, excludes unlinked Feedback, and returns `INSUFFICIENT_EVIDENCE` when none match. `propose` without `--retrospective` and `eval-candidates` without `--proposal` inspect every structurally valid, project-lineage-matching file of the required type: exactly one is selected, zero returns `INSUFFICIENT_EVIDENCE`, and more than one returns `AMBIGUOUS_INPUT` with exit `3`. Selection never prefilters by candidate eligibility.

`--retrospective` accepts only a direct filename or project-relative direct path under `.codex/evolution/retrospectives/`; `--proposal` follows the same rule under `.codex/evolution/candidates/`. Absolute paths, traversal, nested children, symlinks and files with link count other than one are rejected. Filename ID, internal ID, deterministic fingerprint, project fingerprint, source ID and source fingerprint must all agree with validated workspace lineage. External, structurally invalid, fingerprint-invalid or lineage-inconsistent manually created JSON is rejected. As with run ledgers, unsigned local artifacts cannot reveal a coherent rewrite of every related source and fingerprint by an actor with full local write access.

All generated state stays under:

```text
<project>/.codex/evolution/
├── manifest.json
├── outcomes.jsonl
├── feedback.jsonl
├── retrospectives/
├── candidates/
└── eval-candidates/
```

Only `evolution init` creates this workspace for an existing project. Every other mutating Evolution command returns `NOT_INITIALIZED` with exit `3` until initialization succeeds. The v2.1 `init` flow locally generates the workspace for a new project from a Skill-owned template definition; the generated runtime data is not intended to be tracked by the target project's Git repository. Initialization is atomic: it acquires `.codex/.evolution-init-lock`, creates a unique staging directory inside `.codex/`, writes and validates every file, writes `manifest.json` last as the commit marker, and then atomically renames the staging directory into place. The lock uses exclusive creation and is removed in `finally` after a normal attempt; an abandoned lock is never removed automatically. Concurrent initializers cannot overwrite: one succeeds, while the other returns the existing valid workspace idempotently or `BLOCKED`. A partial or incompatible existing directory returns `BLOCKED_PARTIAL_INIT` and is never repaired or overwritten automatically.

A valid project root is an existing directory that contains schema-valid `docs/project-status.json` and `.codex/orchestration/role-plan.json`. `.codex/runs/` is optional until the first run. `collect` or run-linked feedback requires the selected ledger; `collect` with no runs returns `INSUFFICIENT_EVIDENCE`. Evolution commands do not initialize or guess the surrounding project contract.

## 3. Non-goals

v2.1 does not:

- edit the installed Skill, its source repository, approved project documents or formal eval suites;
- commit, push, open a pull request, merge, tag, release or deploy;
- download or install Skills, MCP servers, plugins or executable community code;
- upload, aggregate or synchronize experience across projects;
- write to Obsidian or another knowledge base;
- call an external model or network service for semantic analysis;
- estimate unavailable token, cost, quota, latency, model-use or Agent-liveness facts;
- benchmark or promote a candidate into implementation;
- delete Evolution history automatically.

## 4. Core invariants

- Only Orchestrator writes `.codex/evolution/`.
- Existing run schema `1`, Task Package schema `2`, and routing policy `1.2.0` remain unchanged.
- v2.0 projects remain valid when `.codex/evolution/` does not exist.
- Evolution initialization is additive, idempotent and non-overwriting.
- Inputs are schema-validated and fail closed on corruption or unsupported versions.
- Generated artifacts use project-relative references and cannot escape through absolute paths, traversal or symlinks.
- A retrospective is derived analysis, never approval.
- A proposal is always a draft requiring separate implementation.
- An eval candidate always has `artifact_status=DRAFT` and `review_status=REVIEW_REQUIRED`, and is excluded from the normal `eval` pass count.
- A candidate cannot change its own evidence threshold, acceptance criteria, protected invariants or formal eval expectations.

Protected invariants include development/final-QA separation, one Orchestrator, Worker non-delegation, source-of-truth documents, no silent assumptions, no fake evidence, least privilege, explicit authorization for external or irreversible actions, and non-weakening of lifecycle gates, acceptance criteria and release gates. Evolution policy and its protected registry cannot modify themselves.

## 5. Terminology

- **Structurally validated completed run**: a run whose `run.json`, `checkpoint.json`, `events.jsonl`, `evidence-index.json`, `routing-decisions.json` and `project-snapshot.json` have supported schemas and mutually consistent local lineage. Event sequence is exactly `1..N`; the first event is `RUN_CREATED`; the last event is `RUN_COMPLETED`; every event uses the selected run ID; `checkpoint.last_event_sequence` equals the final event sequence; run status/current state agree with checkpoint and final event; the final `input_fingerprint` agrees across run, checkpoint, final event and project snapshot; run state is `DONE`; checkpoint points to the final event; independent-QA conclusion is `PASS` or `PASS_WITH_ACCEPTED_RISKS`; indexed evidence resolves to ordinary non-symlink files inside the project; and routing history does not extend beyond the final event. Event schema is inferred from run schema `1` for v2 compatibility. Fields absent from the v2.0 run schema, including project fingerprint and a run-level final sequence, are never required there.
- **Outcome**: an allowlisted, sanitized, project-local summary derived from a structurally validated completed run.
- **Feedback**: an explicit correction, defect, routing observation or process observation with project-local evidence.
- **Retrospective**: deterministic aggregation of outcomes and feedback with explicit unknowns and evidence strength.
- **Proposal**: a draft description of a possible Skill/process improvement; it has no execution authority.
- **Eval candidate**: a draft regression scenario that must be independently reviewed before manual promotion to a formal suite.
- **Independent evidence**: a structurally distinct evidence lineage. For a run-linked record, `run_lineage_key = sha256(canonical_json({"project_fingerprint": project_fingerprint, "run_id": run_id}))`, and both Outcomes and all Feedback linked to that run use it. Feedback without a run stores SHA-256 over its sorted canonical evidence-content hashes as its record-level key; during retrospective aggregation, all unlinked Feedback sharing any content hash are merged transitively into one connected evidence cluster, and each cluster counts once per category. Thus `{A}`, `{A,B}`, and `{B}` form one lineage. Splitting one run, overlapping evidence, or the same evidence into several records never increases the independent count. This proves only structural separation in the recorded provenance; it does not prove truth, causal independence or absence of coordinated evidence.
- **UNAVAILABLE**: the runtime did not provide a fact. It is not zero, false, failure or an estimate.

Structural validation detects malformed files, broken sequences, lineage mismatch and internal inconsistency. Because these files are local and unsigned, v2.1 does not claim to detect a coherent malicious rewrite by an actor who can replace all related files.

The v2.0 source compatibility matrix is fail-closed on the required fields below while permitting unknown additional fields for forward-compatible historical records:

| Source | Required structure for collect |
|---|---|
| `run.json` | JSON object; integer `schema_version=1`; canonical string `run_id`; strings `status=DONE`, `start_state`, `current_state=DONE`, `input_fingerprint`, `role_plan_fingerprint`; UTC `created_at` and `updated_at` |
| `checkpoint.json` | JSON object; integer `schema_version=1`; same `run_id`; positive integer `last_event_sequence`; `last_event_type=RUN_COMPLETED`; `last_conclusion=PASS|PASS_WITH_ACCEPTED_RISKS`; `current_state=DONE`; matching string `input_fingerprint` and `role_plan_fingerprint` |
| `events.jsonl` | strict non-empty JSONL within the resource limits; every object has positive integer `sequence`, UTC `timestamp`, same `run_id`, string `event_type`, `status`, `stage_before`, `stage_after`, `input_fingerprint`, `role_plan_fingerprint`; first `RUN_CREATED`; final `RUN_COMPLETED` with `status=DONE` and accepted QA `conclusion` |
| `evidence-index.json` | JSON object; integer `schema_version=1`; arrays `artifacts` and `evidence`; every entry is an object with project-relative string `ref`, nullable canonical `task_id`, UTC `recorded_at`, and positive integer `sequence` not beyond the final event |
| `routing-decisions.json` | JSON object; integer `schema_version=1`; string `role_plan_fingerprint`, string `routing_cycle_id`, string-array `required_now`, and array `history`; each history object has positive integer `sequence` not beyond the final event, UTC `captured_at`, strings `role_plan_fingerprint` and `routing_cycle_id`, and string-array `required_now` |
| `project-snapshot.json` | JSON object with no invented `schema_version` requirement; UTC `captured_at`; strings `current_state`, `input_fingerprint`, `role_plan_fingerprint`, `routing_cycle_id`; string-array `required_now`; other v2.0 snapshot fields are optional historical context |

Cross-file validation compares only fields actually present in the v2.0 contract. A Task Package referenced by feedback is validated only for historical `task_id`, `run_id`, owner/role and indexed-evidence lineage; Evolution never reuses the dispatch preflight rule that requires an OPEN run or a currently dispatchable task. Compatibility tests use fixtures produced by the unmodified v2.0 generator and a completed-run fixture matching its real output.

`evolution init` creates a random immutable `project_instance_id` with 128 bits of entropy. The stable `project_fingerprint` is lowercase SHA-256 over the UTF-8 `project_instance_id`. Both are persisted in the manifest and reused across normal document evolution and filesystem moves; legacy run files are not expected to contain either field. Deleting the workspace and initializing again creates a new project identity and is therefore not an automatic recovery procedure.

## 5.1 Manifest contract

`manifest.json` accepts exactly these keys: `schema_version=1`, `generator_version="2.1.0"`, `policy_version="evolution-1.0.0"`, random UUID-form `project_instance_id`, matching lowercase SHA-256 `project_fingerprint`, UTC ISO-8601 `initialized_at`, and sorted `protected_invariants`. The invariant enum is exactly `single_orchestrator`, `worker_non_delegation`, `development_qa_separation`, `project_docs_source_of_truth`, `no_silent_assumptions`, `no_fake_evidence`, `least_privilege`, `external_action_authorization`, `candidate_non_execution`, `formal_eval_isolation`, `stage_gate_non_weakening`, `acceptance_non_weakening`, `release_gate_non_weakening`, and `evolution_policy_non_self_modification`. Unknown keys, wrong types, unsupported versions, missing invariants or fingerprint mismatch produce `CORRUPT_MANIFEST` or `UNSUPPORTED_SCHEMA` and fail closed.

## 6. Outcome data contract

An outcome accepts exactly these required top-level keys; unknown keys fail validation:

| Key | Type and allowed value |
|---|---|
| `schema_version` | integer `1` |
| `generator_version` | non-empty string |
| `outcome_id` | string matching `OUT-[A-Z0-9-]+` |
| `fingerprint` | lowercase SHA-256 string |
| `independence_key` | lowercase SHA-256 `run_lineage_key` |
| `recorded_at` | UTC ISO-8601 string |
| `project_fingerprint` | lowercase SHA-256 string; never a project name |
| `run_id` | canonical `RUN-*` string |
| `source` | object containing exactly `type=structurally_validated_completed_run`, `run_fingerprint` and `last_event_sequence` |
| `lifecycle` | object containing exactly `start_state` and `final_state` |
| `completion` | object containing exactly `status=DONE` and `qa_conclusion=PASS\|PASS_WITH_ACCEPTED_RISKS` |
| `counts` | object with non-negative integers `events`, `tasks_started`, `handoffs`, `blocks`, `rework`, `artifacts`, `evidence` |
| `planned_routing` | object with string arrays `roles` and `models`; `models` may be empty |
| `actual_execution` | object containing exactly `model`, `reasoning`, `tokens`, `cost`, `quota`, `agent_runtime`, and `attestation_refs`; each fact is `UNAVAILABLE` or a type-valid locally attested value |
| `categories` | unique array drawn from the approved category enum |
| `unknowns` | unique array drawn from `actual_model`, `reasoning`, `tokens`, `cost`, `quota`, `agent_runtime`, `product_quality`, `agent_necessity` |

Approved categories are `business_rule`, `product_completeness`, `ux`, `ui`, `architecture`, `implementation`, `test_coverage`, `model_routing`, `role_routing`, `capability`, `recovery`, `process`, `security_privacy`, and `cost_latency`.

Outcome derivation is fixed: `events` is the number of validated event objects; `tasks_started` counts `TASK_STARTED`; `handoffs` counts `HANDOFF_PERSISTED`; `blocks` counts `TASK_BLOCKED` plus `GATE_DECISION` with `conclusion=BLOCKED`; `rework` counts unique events whose conclusion is `NEEDS_REVISION` or whose `stage_before` differs from `stage_after` and either state starts with `REWORK_`; `artifacts` and `evidence` count unique validated refs in their respective index lists. `planned_routing.roles` is the sorted unique union of `required_now` across validated routing history. Because routing schema 1 does not attest actual model use, `planned_routing.models` is empty. Because run event schema 1 has no structured category field, `categories` is empty and notes are never classified. For every actual-execution fact, a valid attestation means a type-valid value, non-null matching attestation ref and absence of its unknown name; otherwise the value is `UNAVAILABLE`, the ref is `null`, and its unknown name is present.

An outcome must not copy event notes, Prompt text, chat, business document prose, source code, logs, evidence contents, credentials, personal data, customer data, internal URLs or commercial secrets.

An actual-execution value is accepted only from an indexed project-local JSON evidence file with exact schema `schema_version=1`, `type=execution_attestation`, matching `run_id`, approved-role `recorded_by`, UTC `recorded_at`, and an `actual_execution` object containing an allowlisted subset of the six facts. The strict JSON parser rejects `NaN` and infinity. `model` is at most 80 characters, matches `[A-Za-z0-9._:-]+`, and passes the secret-prefix detector; `reasoning` is `none|minimal|low|medium|high|xhigh|max|ultra`; `quota` is `economy|balanced|quality_first`; `agent_runtime` is `STARTED|COMPLETED|FAILED|INTERRUPTED`; `tokens` is a non-negative integer that is not a boolean; and `cost` is a finite non-negative number that is not a boolean. Approved roles are the nine professional roles plus `frontend_worker`, `backend_worker`, `ai_worker`, `data_worker`, and `test_worker`. `attestation_refs` maps each available fact to exactly `path`, `json_pointer`, and `content_hash`; unavailable facts map to `null`. The evidence file is subject to the same containment, file-type, symlink and sensitive-path policy. Any invalid attestation is rejected as a whole and no fact is partially adopted. A planned Task Package or routing decision is never an execution attestation. With no valid attestation, the corresponding value must be the literal `UNAVAILABLE`. This is local provenance, not cryptographic proof.

`outcomes.jsonl` permits at most one record for a `(project_fingerprint, run_id)` lineage. Repeating collect with the same run fingerprint returns the existing outcome. The same run ID with a changed run fingerprint returns `BLOCKED_RUN_LINEAGE_DRIFT` and never appends a second Outcome.

## 7. Feedback data contract

Feedback kinds:

- `user_correction`
- `repeated_defect`
- `routing_waste`
- `model_mismatch`
- `process_gap`
- `security_or_privacy`

Feedback results:

- `CORRECTED`
- `FAIL`
- `BLOCKED`
- `ACCEPTED_RISK`
- `OBSERVED`

Severity is `P0`, `P1`, `P2`, `P3` or `INFO`.

Feedback accepts exactly these top-level keys; unknown keys fail validation:

| Key | Type and allowed value |
|---|---|
| `schema_version` | integer `1` |
| `generator_version` | non-empty string |
| `feedback_id` | string matching `FDB-[A-Z0-9-]+` |
| `fingerprint` | lowercase SHA-256 string |
| `independence_key` | lowercase SHA-256 `run_lineage_key` when `run_id` is present; otherwise SHA-256 over sorted canonical evidence-content hashes |
| `recorded_at` | UTC ISO-8601 string |
| `project_fingerprint` | lowercase SHA-256 string |
| `kind` | approved feedback kind |
| `result` | approved feedback result |
| `severity` | `P0\|P1\|P2\|P3\|INFO` |
| `category` | approved category enum |
| `summary` | one line, 1–500 UTF-8 characters, sanitized before persistence |
| `run_id` | canonical run ID or `null` |
| `task_id` | canonical Task ID or `null` |
| `role` | approved professional/Worker role or `null` |
| `evidence` | sorted unique non-empty array of objects containing exactly `path`, lowercase SHA-256 `content_hash`, and non-negative integer `size_bytes` |

The summary is rejected before persistence when it contains: control characters other than ordinary spaces; a newline; `BEGIN ... PRIVATE KEY`; OpenAI/GitHub token prefixes such as `sk-`, `ghp_`, `gho_`, `ghu_`, `ghs_` or `ghr_`; a three-segment JWT-like token; an email-address pattern; URL userinfo; a URL query key named `token`, `key`, `secret`, `password` or `auth`; or an assignment using `password`, `passwd`, `token`, `secret`, `api_key`, `apikey` or `authorization` followed by a non-placeholder value. The system does not silently persist a partially redacted summary. This narrow detector is not a claim to detect every form of PII; the caller must provide a generic, sanitized summary.

Duplicate feedback fingerprints are idempotent.

Evidence references are metadata only; content is never copied, but path names themselves can still reveal customer or internal information. Each path must be project-relative, at most 512 UTF-8 bytes, resolve within the project, and name an existing regular file. Every parent and target is checked with `lstat`; symlinks, path traversal, hard-linked Evolution ledger files, sockets and devices are rejected. Evidence under `.git/`, `.codex/evolution/`, `.env*`, credential/private-key filenames, and credential-store directories is forbidden. Path components matching an email address, secret/token prefix, JWT-like value, URL-userinfo pattern, or credential-assignment pattern are rejected using the same deterministic sensitive detector as summaries. One feedback record accepts at most 20 evidence files and 10 MiB total. When `run_id` is present, every evidence file must already appear in that run's validated evidence index. `task_id` requires `run_id` and must match Task Package lineage in that run. A supplied role must be an approved role and match the referenced task/run lineage when that lineage attests a role.

## 7.1 Deterministic identity and persistence

Canonical JSON is `json.dumps(value, ensure_ascii=False, sort_keys=True, separators=(",", ":"))`; every fingerprint is lowercase SHA-256 over its UTF-8 bytes. The run fingerprint covers the canonical six run-ledger files plus the sorted project-relative path and content hash of every indexed evidence file. The outcome fingerprint is the run fingerprint. A feedback fingerprint excludes timestamp and generated ID. A retrospective input fingerprint covers sorted source record IDs and fingerprints. A proposal fingerprint covers retrospective fingerprint, normalized category, target and proposal-policy version. An eval-candidate fingerprint covers proposal fingerprint and eval-policy version. Generated IDs use a type prefix plus the first 20 uppercase hexadecimal fingerprint characters, so retries are deterministic.

Run collection limits each ordinary JSON source to 4 MiB, `events.jsonl` to 32 MiB, 100,000 events and 64 KiB per line, the evidence index to 1,000 unique refs, each indexed evidence file to 64 MiB, and all indexed evidence bytes to 512 MiB. Exceeding a limit returns `RESOURCE_LIMIT_EXCEEDED` with exit `3`. Evidence is SHA-256 hashed in 1 MiB streaming chunks. Before and after hashing, `lstat`/`fstat` must agree on device, inode, ordinary-file mode, link count one, size and nanosecond modification time; any change returns `BLOCKED_SOURCE_CHANGED`. Validation and hashing complete before Outcome construction, and no partial Outcome is written.

Evolution JSONL is strict UTF-8. A zero-byte file is a valid empty ledger. A non-empty ledger ends with a final newline, contains no blank lines, and permits exactly one schema-valid JSON object per line. A line is limited to 64 KiB, a ledger to 32 MiB and 100,000 records. IDs and fingerprints must be unique. Any invalid byte, truncated non-empty final line, blank line, non-object, duplicate, unknown key or unsupported schema blocks the Evolution operation; no partial record set is returned.

After initialization, every mutating command acquires `.codex/evolution/.write-lock` using exclusive creation before loading ledgers or making deduplication decisions. `evolution init` instead uses the sibling `.codex/.evolution-init-lock` defined in §2. Each lock contains exact fields `schema_version=1`, `operation`, process ID, hostname, UTC `created_at`, and random nonce. An existing applicable lock returns `BLOCKED_LOCKED` with exit `3`. The lock is removed in `finally` after normal completion, but an abandoned lock is never removed automatically; recovery documentation requires the user to verify no matching process is active, back up the workspace, and explicitly remove that exact lock. Files are written with mode `0600`, directories with `0700`, temporary files stay in the same directory, are flushed and atomically replaced. All validation, fingerprinting and append decisions occur while the lock is held.

## 8. Retrospective rules

A retrospective may use only validated outcomes and feedback. It reports:

- source record IDs and fingerprints;
- counts by category, result, severity, role and run;
- recurring patterns;
- evidence sufficiency for each pattern;
- protected unknowns;
- candidate eligibility and the exact threshold reason;
- generated-at time and input fingerprint.

It must not infer actual model use from a planned Task Package route. It must not claim cost, token, latency, product-quality or Agent-necessity conclusions without attested data.

With no validated records, the result is `INSUFFICIENT_EVIDENCE`; it must not invent a lesson.

Generating the same retrospective from identical inputs is idempotent.

A retrospective JSON object accepts exactly: `schema_version=1`, `generator_version`, deterministic `retrospective_id`, `fingerprint`, `input_fingerprint`, `generated_at`, `project_fingerprint`, `run_scope`, `source_records`, `counts`, `patterns`, `unknowns`, and `candidate_eligibility`. `run_scope` is `null` or a canonical run ID. `source_records` is a sorted unique array of objects containing exactly `type=outcome|feedback`, `id`, `fingerprint`, and `independence_key`; for unlinked Feedback, the persisted key is replaced in aggregation by the deterministic connected-cluster key. `counts` contains exactly non-negative integer `total_records`, non-negative integer `independent_records`, `by_category` with every approved category key, `by_result` with every feedback-result key, `by_severity` with keys in severity order `P0,P1,P2,P3,INFO`, `by_role` with every approved role plus `UNSPECIFIED`, and sorted `by_run` objects containing exactly `run_id`, `records`, and `independent_records`. `patterns` is a category-sorted array; each object contains exactly `category`, `severity_max`, sorted unique `independence_keys`, sorted unique `record_ids`, non-negative `evidence_count`, boolean `eligible`, and enum `threshold_reason=P0_SINGLE|SECURITY_PRIVACY_SINGLE|THREE_INDEPENDENT|INSUFFICIENT`, evaluated in that priority order. `candidate_eligibility` contains exactly sorted unique `eligible_categories`, sorted unique `insufficient_categories`, and `threshold_policy=evolution-1.0.0`. `unknowns` is a sorted unique approved-unknown array. It may state normalized category-level observations but must not copy feedback summaries or evidence contents. Within a category, counts and eligibility deduplicate by run lineage or connected evidence cluster.

## 9. Proposal rules

Ordinary proposal eligibility requires at least three independent evidence records for the same normalized category. One supported feedback record with `severity=P0` or `kind=security_or_privacy` may create a high-priority proposal; merely using category `security_privacy` with another kind does not bypass the ordinary threshold.

Proposal targets are deterministic: `business_rule→template`, `product_completeness→checklist`, `ux→checklist`, `ui→checklist`, `architecture→template`, `implementation→checklist`, `test_coverage→checklist`, `model_routing→model_routing`, `role_routing→role_routing`, `capability→capability_policy`, `recovery→recovery`, `process→prompt`, `security_privacy→capability_policy`, and `cost_latency→model_routing`. One valid retrospective generates exactly one Proposal per eligible category. The command returns sorted `created` and `existing` proposal-ID arrays; identical category fingerprints are idempotently returned as existing. Multiple eligible categories are not ambiguous. `AMBIGUOUS_INPUT` applies only when `--retrospective` is omitted and multiple valid retrospective files are available.

Each proposal contains:

- deterministic proposal ID and source fingerprint;
- `artifact_status=DRAFT` and `review_status=REVIEW_REQUIRED` as independent fields;
- category, priority, title, rationale and falsifier;
- independent outcome/feedback IDs and evidence references;
- proposed target components, but no source patch;
- expected benefit, possible harm, rollback strategy and required evaluation;
- protected invariants;
- explicit flags stating no automatic apply, commit, push, merge or release.

Insufficient evidence returns `INSUFFICIENT_EVIDENCE` and creates no proposal.

Generated proposals remain `artifact_status=DRAFT` until a future, separately authorized workflow performs review. `review_status=REVIEW_REQUIRED` is a gate requirement, not an approval. There is no `APPLIED` or `AUTO_PROMOTED` transition. If a deterministic proposal or eval-candidate filename already exists, it is returned as existing only when the full validated content, project fingerprint and source fingerprint match exactly; any mismatch returns `CORRUPT_ARTIFACT` and never overwrites the file.

A proposal JSON object accepts exactly: `schema_version=1`, `generator_version`, deterministic `proposal_id`, `fingerprint`, `policy_version`, `generated_at`, `project_fingerprint`, `source_retrospective` containing exactly `id` and `fingerprint`, `artifact_status=DRAFT`, `review_status=REVIEW_REQUIRED`, `category`, `priority`, `title`, `rationale_template`, `falsifier`, `independence_keys`, `record_ids`, `evidence_refs`, `target`, `expected_benefit`, `possible_harm`, `rollback_strategy`, `required_evaluation`, `protected_invariants`, `forbidden_changes`, and `authority`. `priority` is always `HIGH` when the selected pattern has `threshold_reason=P0_SINGLE` or `SECURITY_PRIVACY_SINGLE`, even if that category also has three or more independent lineages; only `threshold_reason=THREE_INDEPENDENT` yields `NORMAL`. `target` is one of `role_routing`, `model_routing`, `prompt`, `template`, `domain_pack`, `checklist`, `recovery`, `capability_policy`, or `documentation`. `independence_keys`, `record_ids`, and project-relative `evidence_refs` are sorted unique non-empty string arrays. `protected_invariants` must exactly equal the sorted manifest registry. `forbidden_changes` must exactly equal sorted `acceptance_criteria`, `authorization_rules`, `development_qa_separation`, `evolution_evidence_policy`, `formal_eval_expectations`, `protected_invariant_registry`, `release_gate`, and `stage_gates`. `title`, `rationale_template`, `falsifier`, `expected_benefit`, `possible_harm`, `rollback_strategy`, and `required_evaluation` are selected from category/target-controlled one-line templates of 1–500 UTF-8 characters; they never interpolate Feedback summaries, evidence paths or content. `authority` contains exactly false booleans `auto_apply`, `commit`, `push`, `merge`, and `release`. Proposals cannot contain source patches, commands, executable payloads, network locations or embedded file contents.

Targets are permanently forbidden when they would change the Evolution evidence threshold/policy, protected-invariant registry, formal eval expectations, release gates, authorization rules, development/final-QA separation, or the rule that only one Orchestrator owns global scheduling.

## 10. Eval-candidate rules

An eval candidate is generated only from a valid proposal. It contains:

- schema and generator version;
- independent fields `artifact_status=DRAFT` and `review_status=REVIEW_REQUIRED`;
- proposal/evidence lineage;
- scenario, failure being prevented and acceptance intent;
- suggested deterministic or semantic eval kind;
- fixture requirements, expected invariant and falsifier;
- reviewer checklist and explicit promotion instructions.

It is written only under `.codex/evolution/eval-candidates/`. It remains a draft; `review_status=REVIEW_REQUIRED` does not mean reviewed. The normal `orchestrator.py eval` command must ignore it. It cannot overwrite or amend `evals/routing-v2.json`.

An eval-candidate JSON object accepts exactly: `schema_version=1`, `generator_version`, deterministic `eval_candidate_id`, `fingerprint`, `policy_version`, `generated_at`, `project_fingerprint`, `source_proposal` containing exactly `id` and `fingerprint`, `artifact_status=DRAFT`, `review_status=REVIEW_REQUIRED`, `scenario`, `prevented_failure`, `acceptance_intent`, `suggested_eval_kind`, `fixture_requirements`, `expected_invariant`, `falsifier`, `reviewer_checklist`, and `promotion_instructions`. `suggested_eval_kind` is `deterministic` or `semantic_review`. `fixture_requirements` and `reviewer_checklist` are sorted unique arrays of one-line strings, each 1–300 UTF-8 characters. `scenario`, `prevented_failure`, `acceptance_intent`, `expected_invariant`, and `falsifier` are one-line strings of 1–500 UTF-8 characters. All text rejects control characters and newlines. `promotion_instructions` is the fixed string `Independent reviewer must manually validate and copy this case into a formal suite; this artifact performs no promotion.`

## 11. Compatibility and recovery

- A v2.0 project receives Evolution files only after an explicit `evolution init`.
- Existing files are never overwritten; an incompatible manifest blocks with remediation.
- Existing v2.0 runs are readable when their structurally validated completion contract is intact.
- Older events without optional routing metadata remain valid; unavailable facts are reported as `UNAVAILABLE`.
- Corrupt or truncated Evolution data blocks only Evolution commands. Core lifecycle, resume, formal routing eval and existing project validation remain usable. The user repairs or restores the ledger; the system does not skip malformed lines and learn from a partial set.
- Evolution output failure does not mutate a completed run or its checkpoint.
- Rolling the Skill back to v2.0 leaves `.codex/evolution/` unused but does not break core project commands.
- No automatic purge is provided in v2.1; retention is local and indefinite until the user chooses a later explicit policy.
- Evolution data should remain untracked and ignored because it can reveal project process metadata. A new-project template includes the target rule `.codex/evolution/` in its generated `.gitignore`, then locally initializes the ignored workspace. For an existing project, `evolution init`, `status` and `doctor` inspect Git state without changing it. `status` always remains available, and `init` may create only the empty workspace plus a warning. In a Git repository, `collect`, `feedback`, `retrospect`, `propose` and `eval-candidates` write only after `.codex/evolution/` is confirmed ignored and no Evolution path is tracked. If Git state cannot be determined, the path is unignored, or any Evolution file is tracked, every such write returns `GIT_EXPOSURE_RISK` with exit `3`; there is no override flag. The system never edits `.gitignore`, deletes data, changes the index or rewrites history. Outside a Git work tree, local writes are allowed. Backup, migration, retention and manual cleanup are documented as explicit user-controlled operations.

## 12. Status behavior

`evolution status` is read-only and reports:

- workspace state: `NOT_INITIALIZED`, `READY` or `BLOCKED`;
- schema/policy mode;
- outcome, feedback, retrospective, proposal and eval-candidate counts;
- latest artifact IDs;
- any unsupported schema or corruption;
- Git exposure risk and an exact reason code;
- the next safe action.

Workspace/status reason codes are `OK`, `NOT_INITIALIZED`, `BLOCKED_PARTIAL_INIT`, `BLOCKED_LOCKED`, `UNSUPPORTED_SCHEMA`, `CORRUPT_MANIFEST`, `CORRUPT_LEDGER`, `CORRUPT_ARTIFACT`, `PATH_POLICY_VIOLATION`, and `GIT_EXPOSURE_RISK`. Operation-level reason codes additionally include `INSUFFICIENT_EVIDENCE`, `AMBIGUOUS_INPUT`, `BLOCKED_RUN_LINEAGE_DRIFT`, `BLOCKED_SOURCE_CHANGED`, and `RESOURCE_LIMIT_EXCEEDED`. Counts and latest IDs are reported only after complete validation; otherwise those fields are the literal `UNAVAILABLE`, never a partial count. Status does not create the workspace, repair data or approve a candidate.

## 13. Acceptance criteria

- `AC-EVO-01`: Projects created from the v2.1 project template include a valid local Evolution workspace without network or third-party dependencies.
- `AC-EVO-02`: Existing v2.0 projects remain valid without Evolution files and can add them non-destructively.
- `AC-EVO-03`: Collect accepts a structurally consistent completed run and rejects OPEN, BLOCKED, field/sequence/fingerprint/lineage-inconsistent or corrupt completion state; it does not claim detection of a coherent malicious rewrite of all unsigned local files.
- `AC-EVO-04`: Collect is idempotent for the same completed run.
- `AC-EVO-05`: Outcome files contain only allowlisted structure and explicit `UNAVAILABLE` facts; they do not copy notes or evidence contents.
- `AC-EVO-06`: Feedback requires existing project-local evidence, rejects path escape and suspicious sensitive text, and is idempotent.
- `AC-EVO-07`: Corrupt, truncated, non-object or unsupported-schema JSONL fails closed.
- `AC-EVO-08`: Retrospect returns `INSUFFICIENT_EVIDENCE` for empty inputs and deterministic results for unchanged inputs.
- `AC-EVO-09`: Ordinary proposals require three independent evidence records; P0/security proposals may use one supported record.
- `AC-EVO-10`: Proposal generation creates draft metadata only and cannot modify Skill source, project truth, formal evals, Git or external systems.
- `AC-EVO-11`: Eval candidates keep `artifact_status=DRAFT` and `review_status=REVIEW_REQUIRED`, stay outside the formal suite and do not affect pass counts.
- `AC-EVO-12`: Status is read-only and reports unsupported schema or corruption accurately.
- `AC-EVO-13`: Existing 68 tests and 18 routing evals continue to pass without weakened assertions.
- `AC-EVO-14`: New unit/CLI/security tests cover no-run, duplicate, corruption, schema mismatch, path traversal, symlink escape, evidence insufficiency and candidate isolation.
- `AC-EVO-15`: Python 3.9, 3.11 and 3.13 CI, archive smoke test, Skill validation, doctor, README commands and fresh install all pass.
- `AC-EVO-16`: Omitted selectors are deterministic: zero, one and multiple structurally valid project-matching inputs produce the specified result, including `AMBIGUOUS_INPUT` rather than a guessed latest or prefiltered eligible file.
- `AC-EVO-17`: Only explicit `evolution init` creates an existing project's workspace; initialization is atomic, non-overwriting and detects partial initialization.
- `AC-EVO-18`: Independent-evidence counting deduplicates the same run and evidence lineage even when split across multiple records.
- `AC-EVO-19`: Evidence validation enforces file type, containment, symlink, forbidden-path, size/count and supplied run/task/role lineage rules.
- `AC-EVO-20`: Exact retrospective, proposal and eval-candidate schemas, canonical fingerprints and project lineage are validated on read and write.
- `AC-EVO-21`: Cross-process locking and atomic writes prevent lost updates, duplicate append decisions and partial ledgers; stale locks require explicit human recovery.
- `AC-EVO-22`: Evolution corruption or absence never blocks v2 core lifecycle, resume or formal eval; doctor reports the optional-layer problem without treating the core project as invalid.
- `AC-EVO-23`: Git exposure and retention risks are surfaced without automatic ignore-file changes, deletion or network transfer, and the user guide demonstrates the complete init-to-eval-candidate command chain.
- `AC-EVO-24`: Overlapping unlinked evidence sets such as `{A}`, `{A,B}`, and `{B}` form one connected evidence lineage and cannot satisfy the three-lineage threshold.
- `AC-EVO-25`: Retrospective/proposal selectors accept only direct ordinary workspace files with matching filename, ID, project and source fingerprints; external, nested, linked, structurally invalid or lineage-inconsistent manually created JSON is rejected without claiming detection of a coherent rewrite of every unsigned local source.
- `AC-EVO-26`: In a Git work tree, every Evolution write after init is blocked until the runtime directory is confirmed ignored and untracked; indeterminate Git state fails closed without modifying Git.
- `AC-EVO-27`: Unmodified v2.0-generated run fixtures and a completed historical fixture pass the explicit six-file compatibility matrix without reusing OPEN-run dispatch checks.
- `AC-EVO-28`: Run collection enforces JSON/event/evidence resource limits, uses streaming stable-file hashing, and writes no Outcome on size excess or concurrent source change.
- `AC-EVO-29`: Every Proposal carries the full protected registry and forbidden-change set; controlled templates cannot weaken stage, acceptance, QA, release, authorization, formal-eval or Evolution-policy gates.
- `AC-EVO-30`: Threshold priority is `P0 > security_or_privacy > three independent`; categories with three lineages that also contain P0 or `security_or_privacy` still generate HIGH priority; selector, insufficient-evidence, lineage-drift, source-change and existing-artifact-mismatch outcomes use one deterministic reason code and exit contract.

## 14. Release boundary

Local implementation, tests, documentation and candidate packaging are authorized. GitHub push, `v2.1.0` tag and public Release require a separate explicit authorization after independent QA and Quality Governor approval.
