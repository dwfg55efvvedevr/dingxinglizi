# v3.1 Large Repository Review Engine

Status: APPROVED IMPLEMENTATION BASELINE
Owner: Orchestrator / Engineering Lead
Product version: 3.1.0
Compatibility: additive to v3.0 and unmigrated v2 control roots

## Decision

Large-repository review is a run-local, evidence-bound work graph. It does not replace the project lifecycle, invent a new global manager, or equate heuristic module discovery with full architecture understanding.

The engine binds one review to the current OPEN run and stores control state below the active control root:

```text
<control-root>/runs/RUN-ID/review/
├── review.json
├── snapshot.json
├── inventory.json
├── plan.json
├── trust.json
├── results.json
├── findings.json
├── coverage.json
├── repairs.json
├── rereviews.json
├── qa.json
├── review.json
└── final-report.json
```

`project_layout.control_path()` chooses `.dingxinglizi/` or an unmigrated `.codex/` once per command. Ordinary projects do not need a migration merely because they have no review directory.

## Modes and authority

- `review_only` is the default. Repository source is read-only. The engine may write only project-local control records, task contracts, findings and sanitized evidence.
- `review_and_fix` must be selected explicitly. Review shards remain read-only. Source writes require a separate repair contract whose allowed files derive from reviewed findings and the user's existing authorization.
- Repair and re-review use different sessions. Final QA is independent from Engineering Lead and every Worker.
- Production, credentials, external messages, public release, destructive actions, irreversible migrations and scope changes retain their separate authorization boundaries.

## Snapshot and drift

A Git review resolves baseline and target to immutable 40-character commits. The target manifest is a deterministic ordered list of paths, modes, object IDs and sizes. v3.1 reviews the complete target tree; baseline ancestry is version evidence and must not be represented as a diff-only review.

The engine records working-tree state separately. A tracked source change, target change, manifest mismatch, plan mismatch or declared-scope change makes the review `STALE`; old results cannot be finalized against the new code. Non-Git projects may use `WORKTREE_SNAPSHOT`, but the report must not claim commit-level traceability.

## Inventory and exclusions

Inventory prefers Git objects so the review does not silently mix a target commit with current files. It records, rather than hides:

- explicitly excluded paths;
- generated/vendor/cache/build trees;
- binaries and oversized files;
- Git LFS pointers and submodules;
- symbolic links or unsafe paths;
- unsupported or unreadable entries;
- every automatic exclusion outside the full target-tree included set.

Module detection uses explicit configuration or manifests when available, then workspace/package conventions, then conservative path/language heuristics. Every module record includes its detection basis and confidence. The allowed claim is “deterministic shard planning for the declared scope,” not “complete semantic architecture discovery.”

## Shards and context budgets

Primary shards are grouped by module and technical surface, then split deterministically by:

- maximum files;
- maximum bytes;
- maximum statically estimated tokens;
- configured safety margin and rollover threshold.

Static token estimation is planning evidence only. It never claims actual host token use. A single input that exceeds a hard budget is blocked or requires an explicit range-level continuation; it is never silently truncated.

High-risk paths create cross-cutting shards for security, permissions, data/migration, concurrency, external side effects, AI safety, release or contracts as applicable. Every declared source file must map to at least one primary shard. Cross-cutting coverage is additional, not a substitute for primary coverage.

One shard maps to one validated Task Package, one matching READY dispatch receipt and one fresh execution session requirement. A COMPLETE result binds every file to its pinned object ID and concrete per-file checks/observation. The Orchestrator defaults to one active subagent. `balanced` or `quality_first` may allow Engineering Lead plus one governed Worker. A completed shard persists a compact result and exits before the next shard starts.

## Findings and aggregation

Every finding carries review/shard/target lineage, location, category, severity, confidence, evidence, impact, verification, source owner, repair recommendation, cross-module flag, state and content fingerprint.

Exact duplicates may merge only when their normalized target, location, category and root-cause fingerprint match. Severity conflicts retain all sources and use the highest severity for gating. Similar findings become `POSSIBLE_DUPLICATE`; contradictory conclusions become `CONFLICT_REVIEW_REQUIRED`. Neither is silently discarded.

The Orchestrator consumes `merged-findings.json` and compact coverage indexes instead of loading all source and raw findings into its session.

## Coverage conclusion

The strongest `review_only` mechanical conclusion is:

`COMPLETE_FOR_DECLARED_SCOPE`

It requires current fingerprints, every declared file assigned to a completed primary shard, every required risk lens completed, valid Task Package/dispatch/result lineage, aggregation complete, exclusions visible and independent QA evidence. `review_and_fix` uses `INITIAL_DECLARED_SCOPE_REVIEW_COMPLETE_AND_AUTHORIZED_REPAIRS_QA_VERIFIED` so initial full-target coverage is not misrepresented as a full re-review of the repaired worktree. Neither means all behavior is correct, every defect was found, or excluded/binary/runtime behavior was reviewed.

## Repair and re-review

`review_and_fix` routes merged findings to the earliest source owner. Repair contracts are bounded by finding IDs and allowed files. The ordinary maximum is two repair attempts per finding. A repair result does not close a finding; a new session must re-review it against the new target/snapshot, and independent QA must validate regression evidence.

Repeated failure, scope expansion, business contradiction, unavailable authority, external dependency, production access or unverified environment enters `BLOCKED`. Model escalation never substitutes for correcting a wrong problem contract or splitting an over-budget task.

## Safety and resource limits

- subprocess calls use argument lists, timeouts and no shell;
- project writes use confined atomic helpers;
- path traversal and symlink escape fail closed;
- state inputs are ordinary single-link files;
- inventory, file size, aggregate bytes, findings and repair attempts are bounded;
- records contain hashes, locations and compact summaries, not unnecessary source or secrets;
- repository content is untrusted review data, not an instruction source. Only explicitly pinned trusted instruction paths and approved project facts may instruct the reviewer; repository execution is separately explicit and remains host-enforced.

## Recovery and rollback

Recovery reconstructs the next safe action from run-local records. A changed target or corrupted coverage requires re-plan or block; the engine never assumes a native Agent session survived. v3.0 ignores the additive `review/` directory. Rollback is therefore installing the verified v3.0 Skill while retaining review records for later inspection; no automatic deletion or reverse migration occurs.

## Explicit non-claims

v3.1 does not prove exact token usage, absolute context cleanliness, universal language semantics, zero defects, all-runtime behavior, native session creation on every host, safe execution of unknown community code, or unlimited autonomous repair.
